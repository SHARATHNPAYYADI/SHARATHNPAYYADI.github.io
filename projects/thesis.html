Overview

Industrial warehouses and smart factories increasingly deploy fleets of Autonomous Mobile Robots (AMRs) from multiple vendors — but getting them to share narrow corridors and intersections without collision or deadlock is a hard, unsolved coordination problem.

This thesis, carried out at Node Robotics GmbH (a Fraunhofer IPA spin-off), presents a centralized traffic management system built on top of a topological graph representation of the environment. The system proactively detects path conflicts, generates collision-free detour routes where possible, and falls back to intelligent waiting strategies when rerouting is infeasible — all communicated to heterogeneous robot fleets via the VDA5050 standard protocol over MQTT.

Fleet Management System overview — the FMS coordinates heterogeneous robot fleets (MiR, Geek+, and others) through a unified AGV/AMR fleet manager using the VDA5050 communication standard over MQTT.

The Problem

Existing traffic managers relied on hard-coded rules on fixed graphs and delegated collision avoidance entirely to each robot's local planner. This broke down in narrow corridors where two robots would book overlapping paths and deadlock — with no mechanism to detect or resolve the conflict proactively.

💥
Path collisions
Two robots booking opposing paths in single-lane corridors caused full deadlocks
🔒
No detour logic
Existing system had no mechanism to reroute a robot when its planned path was blocked
🚫
Traffic rules ignored
Robot size and corridor width not considered — all robots treated identically regardless of footprint
⏳
Inefficient waiting
Robots stalled at their start position rather than advancing to the nearest safe waiting spot

Approach

The environment is modelled as a topological graph — sections, corridors, crossings, and Points of Interest (POIs) — derived from a metric occupancy grid map. The traffic manager operates on this graph to make proactive, robot-aware routing decisions before issuing VDA5050 orders.

Step 1
Graph environment
Topological map with sections, crossings, traffic rules (ONE_WAY / TWO_WAY, LEFT / RIGHT / CENTER)
Step 2
Robot tracking
VDA5050 feedback decoded via lookup table — real-time position mapped to graph segments
Step 3
Conflict detection
Path overlaps and narrow-corridor incompatibilities detected using robot radii
Step 4
Resolution
Detour path generated if feasible; else safe waiting spot calculated 2 nodes before conflict
Step 5
Order dispatch
VDA5050 order issued to robot over MQTT; execution monitored until goal reached
Topological graph of the factory environment — red circles represent graph nodes (control points), blue lines are edges defining valid navigation paths between them. Points of Interest (poi1, poi2, poi3) mark robot parking and task locations. This graph is the foundation for all traffic decisions in the system.

Key Contributions

Conflict Detector
Checks path overlaps for all active robots. Uses robot radii vs corridor width to determine whether two robots can physically pass in opposite directions (may_cross logic). Robots following the same direction are correctly allowed through.
Dynamic Detour Generator
When a conflict is detected, the system searches for an alternative path through the topological graph. If the detour itself causes further conflicts, it is discarded — preventing cascading deadlocks before they occur.
Safe Spot Calculator
When detouring is infeasible, the lower-priority robot advances to the nearest safe waiting position (two graph nodes before the conflict point) rather than stalling at its origin, keeping the rest of the path clear.
Order Prioritizer
First-come-first-serve priority assignment determines which robot proceeds and which waits or detours. Architecture is extensible to distance-based or mission-critical priority schemes.
Heterogeneous Fleet Support
Robot-specific properties (radius, speed, dimensions) are factored into every traffic decision. Tested on MiR100 and Geek+ robots with different footprints operating simultaneously in the same environment.
ROS2 Service + CI/CD Tests
Detour logic exposed as a standalone ROS2 service. Google Test suite covering all key conflict scenarios integrated into the CI/CD pipeline for regression safety.

System Architecture

The system sits inside the Fleet Server and consists of two tightly coupled layers communicating via MQTT / VDA5050:

Fleet Management Layer

  • Traffic Manager (conflict detection, detour, priority)
  • Fleet Manager (task allocation, mission flow)
  • Preprocessor → Scheduler → Decomposer pipeline
  • REST API for mission submission
  • Graph Environment (topological + spatial)

Robot Layer

  • Robot Controller (VDA5050 order parser)
  • Behaviour tree for edge/node execution
  • Status aggregator (real-time pose feedback)
  • Local planner for dynamic obstacle avoidance
  • RViz visualization for path validation
Traffic management system architecture — the Fleet Server hosts the Traffic Manager and Fleet Manager. Missions are dispatched to individual robots via MQTT using the VDA5050 protocol. Robots report back their real-time position and order state, which the Fleet Server uses to continuously update traffic decisions.

Results & Scenarios Tested

The algorithm was validated across four distinct multi-robot scenarios in RViz simulation, and subsequently deployed on real MiR100 and Geek+ robots. Each scenario demonstrates a different conflict resolution strategy:

Scenario 1
Narrow corridor — dynamic detour
robot_A (poi1→poi3) and robot_B (poi2→poi1) planned conflicting paths through a single-lane corridor that cannot fit two robots simultaneously. The conflict detector flags the overlap; the detour generator finds an alternate path for robot_B.
✓ robot_B dynamically rerouted via alternate outer path — zero collision, no waiting
Scenario 2
Narrow corridor — safe wait
robot_B (poi1→poi2) has priority. robot_A (poi3→poi1) cannot detour without creating a new conflict. The safe spot calculator directs robot_A to wait two nodes before the collision point.
✓ robot_A advanced to optimal wait position and resumed automatically after robot_B cleared
Scenario 3
Intersection crossing — node reservation
Two robots approach a shared crossing node from different directions. robot_A arrives first and reserves the crossing. robot_B drives to its connecting node and waits. As robot_A clears, robot_B is released to cross.
✓ Clean sequential crossing — no deadlock, no collision, minimal wait time
Scenario 4
Three robots — cascading detour
robot_B (poi10→poi9), robot_C (poi9→poi3), robot_A (poi3→poi9) all operating simultaneously. robot_C and robot_B share a very narrow corridor; robot_A shares the same corridor as robot_B.
✓ robot_C and robot_A both rerouted independently — robot_B proceeded on original path
T-crossing sequence (left→right, top→bottom) — both robots initially reserve up to the connecting node before the crossing. robot_A arrives first and claims the T-crossing node. robot_B drives to its waiting position. Once robot_A clears the middle section, robot_B is released and the scenario transitions into a chase sequence. This demonstrates the conservative lease reservation strategy in action.

Future Work

The thesis establishes a solid foundation with clear extension points: real-world deployment in full-scale factory environments, integration of a local planner for static obstacle awareness within the traffic manager, distance- or mission-critical priority scheduling, and scaling to fleets beyond three robots across larger and more complex graph topologies.
