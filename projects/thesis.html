Overview

Industrial warehouses and smart factories increasingly deploy fleets of Autonomous Mobile Robots (AMRs) from multiple vendors — but getting them to share narrow corridors and intersections without collision or deadlock is a hard, unsolved coordination problem.

This thesis, carried out at Node Robotics GmbH (a Fraunhofer IPA spin-off), presents a centralized traffic management system built on top of a topological graph representation of the environment. The system proactively detects path conflicts, generates collision-free detour routes where possible, and falls back to intelligent waiting strategies when rerouting is infeasible — all communicated to heterogeneous robot fleets via the VDA5050 standard protocol over MQTT.

The Problem

Existing traffic managers relied on hard-coded rules on fixed graphs and delegated collision avoidance entirely to each robot's local planner. This broke down in narrow corridors where two robots would book overlapping paths and deadlock — with no mechanism to detect or resolve the conflict.

💥
Path collisions
Two robots booking opposing paths in single-lane corridors caused full deadlocks
🔒
No detour logic
Existing system had no mechanism to reroute a robot when its planned path was blocked
🚫
Traffic rules ignored
Robot size and corridor width not considered — robots of different dimensions treated identically
⏳
Inefficient waiting
Robots waited at their start position rather than advancing to the nearest safe spot

Approach

The environment is modelled as a topological graph — sections, corridors, crossings, and Points of Interest — derived from a metric occupancy grid map. The traffic manager operates on this graph to make proactive, robot-aware routing decisions before issuing VDA5050 orders.

Step 1
Graph environment
Topological map with sections, crossings, traffic rules (ONE_WAY / TWO_WAY, LEFT / RIGHT / CENTER)
Step 2
Robot tracking
VDA5050 feedback decoded via lookup table — real-time position mapped to graph segments
Step 3
Conflict detection
Path overlaps and narrow-corridor incompatibilities detected using robot radii
Step 4
Resolution
Detour path generated if feasible; else safe waiting spot calculated 2 nodes before conflict
Step 5
Order dispatch
VDA5050 order issued to robot over MQTT; execution monitored until goal reached

Key Contributions

Conflict Detector
Checks path overlaps for all active robots. Uses robot radii vs corridor width to determine whether two robots can physically pass in opposite directions (may_cross logic).
Dynamic Detour Generator
When a conflict is detected, the system searches for an alternative path through the topological graph. If the detour itself causes further conflicts, it is discarded — preventing cascading deadlocks.
Safe Spot Calculator
When detouring is infeasible, the lower-priority robot advances to the nearest safe waiting position (two graph nodes before the conflict point) rather than stalling at its origin.
Order Prioritizer
First-come-first-serve priority assignment determines which robot proceeds and which waits or detours — extensible to distance-based or custom priority schemes.
Heterogeneous Fleet Support
Robot-specific properties (radius, speed, dimensions) are factored into every traffic decision. Tested on MiR100 and Geek+ robots with different footprints.
ROS2 Service + CI/CD Tests
Detour logic exposed as a standalone ROS2 service. Google Test suite covering all key scenarios integrated into the CI/CD pipeline for regression safety.

System Architecture

The system sits inside the Fleet Server and consists of two tightly coupled layers communicating via MQTT / VDA5050:

Fleet Management Layer

  • Traffic Manager (conflict detection, detour, priority)
  • Fleet Manager (task allocation, mission flow)
  • Preprocessor → Scheduler → Decomposer pipeline
  • REST API for mission submission
  • Graph Environment (topological + spatial)

Robot Layer

  • Robot Controller (VDA5050 order parser)
  • Behaviour tree for edge/node execution
  • Status aggregator (real-time pose feedback)
  • Local planner for dynamic obstacle avoidance
  • RViz visualization for path validation

Tech Stack

Results & Scenarios Tested

The algorithm was validated across four distinct multi-robot scenarios, demonstrating correct conflict resolution in each case:

Scenario 1
Narrow corridor — detour
robot_A (poi1→poi3) and robot_B (poi2→poi1) planned conflicting paths through a single-lane corridor.
✓ robot_B dynamically rerouted via alternate path — zero collision
Scenario 2
Narrow corridor — wait
Conflict detected but no feasible detour exists. robot_A directed to safe waiting spot before conflict node.
✓ Robot advanced to optimal wait position, resumed after robot_B cleared
Scenario 3
Two-way corridor — pass-through
Robots on opposing paths in a wide two-way corridor. Width check confirms both robots can pass simultaneously.
✓ No conflict flagged — both robots proceeded without intervention
Scenario 4
Three robots — complex detour
robot_A, robot_B, robot_C with crossing paths in a complex environment with multiple narrow sections.
✓ robot_C and robot_A both dynamically rerouted; robot_B followed original path

Future Work

The thesis establishes a solid foundation with clear extension points identified: real-world deployment in full-scale factory environments, integration of a local planner for static obstacle awareness, distance- or priority-based order scheduling, and scaling to fleets beyond three robots with more complex graph topologies.
