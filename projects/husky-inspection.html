📌 Overview

A simulation-first inspection stack for the Clearpath Husky UGV, built incrementally on top of the upstream Clearpath ROS2 packages: navigation and localization first, then a behavior-tree-driven multi-waypoint mission system, then AI-based inspection. A YOLO fire-extinguisher detector now runs at every waypoint during each mission, flagging it as found or missing in an auto-generated report — all launchable and controllable from a FastAPI + web dashboard with live teleop and mission telemetry.

🗺️ Simulation Environment

A custom construction-site world in Gazebo, localized against a SLAM-built occupancy map. Five inspection waypoints are recorded on the map, each aligned to a wall-mounted fire extinguisher the robot checks for during a mission — Point 2 currently reports missing.

⚙️ Key Engineering Decisions

1
Navigation reliability before mission logic
Development was staged deliberately: Gazebo simulation and Nav2/AMCL localization against a static map were validated first, with automatic initial-pose setting removing the manual RViz step, before any mission orchestration was layered on top.
2
Behavior tree for multi-waypoint missions, not a linear script
husky_mission_bt loops navigate → inspect → publish-result per waypoint via BehaviorTree.CPP, driven by husky_mission_interface's /start_mission_sequence service — giving the mission a cancellable, resumable structure instead of a single blocking function.
3
Vision inspection layered on top, not baked into navigation
The YOLO fire-extinguisher detector (husky_vision_detector) and image_capture_service run as a separate inspection step the BT calls at each waypoint, keeping detection swappable independently of the navigation/mission stack.
4
Auto-generated report on mission completion
The dashboard backend tracks incoming mission_results against the expected waypoint count; once they match, it fires an internal report generator that fills an HTML template with per-point images and found/missing status — no manual "generate report" step needed.
5
Real-time teleop over WebSocket, control over REST
High-frequency joystick velocity commands go over a persistent WebSocket straight to /cmd_vel for low latency, while lower-frequency actions (go-to-goal, capture, start/stop mission) use simple REST calls — matched to how often each actually needs to fire.

📊 Results

  • Stable Nav2/AMCL localization and automatic initial pose setting in a custom Gazebo construction-site world
  • Behavior-tree-driven multi-waypoint mission execution with cancel support, triggered from a single service call
  • YOLO-based fire-extinguisher detection running per waypoint, feeding found/missing status straight into the report
  • Auto-generated per-mission HTML reports with captured/annotated images, no manual step required
  • Unified web dashboard for manual joystick teleop and autonomous missions, with a decoupled frontend reusable against a mocked demo backend
